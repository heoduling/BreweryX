# BreweryX 3.7.1-1 修复与验证

基于上游 `0ceed4aa933012c049dc69ad84c565ad2c7ceb63`（3.7.1）。本分支面向用户的 Folia/Shiroha 环境，不承诺 Spigot 兼容。

## 日志结论

- 粘贴日志的 07:07:04 告警，与 latest (6).log 中 15:09:56、16:58:58 两个 BreweryX 调用栈同属容器快照路径。前两处命中 `InventoryListener.onInventoryClick`，后一处命中 `onInventoryClickBSealer`。
- 生产 JAR 与最新版都通过 `PaperLib.getHolder(..., true)` 获取 Holder。实际生产栈走 PaperLib 的 `InventoryHolderSnapshotBeforeSnapshots`，它直接调用无参 `Inventory.getHolder()`。匹配核心字节码证实，此调用对方块容器进入 `getOwner → getState → createSnapshot`，重新解码内部物品。仅把 PaperLib 的 true 改为 false 无法纠正这个回退分支。
- 本补丁对身份识别改用原生 `getHolder(false)`，覆盖桶点击、拖拽、封酒机点击、关闭、酿造台漏斗检查、封酒机初始化及 LogBlock 关闭识别。没有把容器访问移到异步线程。MCBarrel 与 BDistiller 需要更新方块状态的快照路径保留。
- 采样堆栈证明了昂贵调用路径，不能证明整个 30.9 秒都花在该函数，也不能证明死锁或物品损坏。本次没有生产物品 NBT，未声称复现原现场停顿时长。
- 日志里的三种“找不到配方”与快照问题不同。按用户后续明确指示，配方、启用状态、名称和其处理逻辑全部不改。

## 呕吐

- 生产 3.7.0 JAR 在两个相距 2048 格的玩家同时呕吐时，实际复现 `Cannot add entity off-main thread`。共享呕吐任务在一个玩家的区域处理另一名玩家的掉落物。上游提交 `91639e843b60eab62ff0b16c3243b23e2766f4df` 已改为每玩家独立任务；交付版包含该修复。同条件下上游 3.7.1 和交付版均未出现这条跨区域异常。
- 额外复现 `pukeDespawntime: 1` 导致 `Random.nextInt(0)` 抛异常，现保证随机数上界至少为 1。用户提供的值是 60，此项是边界修复，不是对其现场原因的猜测。
- 呕吐路径写入的 `brewery_puke` Metadata 在整个插件中没有读取方；实际生成并移除 128 个物品后仍保留标记。删除无用途的写入，避免继续累积。漏斗防拾取仍依赖原有拾取延迟与物品类型，未修改。外部附加插件是否私下读取该未文档化标记没有验证；本次未提供附加插件。
- 原配置 `enablePuke: false` 保持不变。本补丁不会自动为服主开启功能。

## 安装与回滚

1. 正常停服，备份原 JAR 和完整 `plugins/BreweryX/` 目录。
2. 移走旧 JAR，放入 `BreweryX-3.7.1-1.jar`，保留原配置和数据目录，不要同时放两份 BreweryX。
3. 正常启动，检查普通木桶、酿酒桶和封酒机，再按需求开启呕吐。没有必要重建数据，也不要更改 encodeKey。
4. 如需回滚，停服后恢复旧 JAR；需要恢复整个备份时连同其同期数据一起恢复。

未接触或部署生产服务器。此交付按正常停服更新验证，不提供热卸载/热替换保证。
